Descripción del Proyecto
El "Proyecto 21" consiste en el desarrollo de una plataforma web para el sector ferretero que integra Inteligencia Artificial para optimizar las consultas de inventario. El sistema está diseñado para procesar entradas de texto informales, comprender la intención del cliente mediante procesamiento de lenguaje natural (NLP) y devolver coincidencias exactas y sugerencias de productos sustitutos en tiempo real, operando bajo un modelo distribuido de Arquitectura Limpia (
Clean Architecture
).
Objetivo General
Desarrollar un Buscador Inteligente para Ferreterías capaz de interpretar el lenguaje coloquial o las descripciones imprecisas de los usuarios, vinculándolas automáticamente con la terminología técnica del inventario, para mostrar el código exacto (SKU), la imagen del producto y sus alternativas sustitutas.
Objetivos Específicos
Diseñar una interfaz de usuario (UI/UX) minimalista e intuitiva que permita la captura de consultas en lenguaje natural, reduciendo drásticamente la carga cognitiva del cliente.
Desarrollar una lógica de servidor (
Backend
) bajo el patrón de Arquitectura Limpia que actúe como puente entre la capa de presentación y la base de datos, implementando estrategias de Caché en Memoria para optimizar el rendimiento y la latencia.
Orquestar un flujo de automatización reactivo que integre el motor de Inteligencia Artificial para evaluar equivalencias técnicas y gestionar casos de inventario vacío de forma segura en una base de datos relacional.
Bajo el Enfoque Ágil (Adaptativo)
1. Premisa Metodológica
Para el desarrollo de este Buscador Inteligente, se descartó de plano el enfoque predictivo tradicional (en cascada), dado que el proyecto involucra tecnologías altamente dinámicas como la Inteligencia Artificial. En su lugar, se adoptó el Enfoque Ágil (Adaptativo). Este paradigma se fundamenta en el control empírico de procesos, priorizando la entrega continua de incrementos de software funcionales y asumiendo la volatilidad de los requisitos como una constante natural del desarrollo.
1.1. Justificación según la Matriz de Selección Metodológica
La elección del paradigma ágil se sustenta en los siguientes criterios críticos del proyecto:
Incertidumbre de Requisitos (Alta):
 El sistema utiliza Inteligencia Artificial para interpretar lenguaje coloquial impreciso, lo que hace que el alcance técnico inicial sea exploratorio, heurístico y sujeto a ajustes.
Frecuencia de Retroalimentación (Continua):
 Se requirieron demostraciones, pruebas de carga (SQA) y ajustes constantes en los 
prompts
 y en la latencia del motor de búsqueda.
2. Gestión de Requisitos (Product Backlog)
Siguiendo los preceptos del Manifiesto Ágil, los requisitos no fueron "congelados" al inicio del proyecto. La funcionalidad central del buscador (procesamiento de lenguaje natural, traducción técnica y recomendación de sustitutos) se gestionó mediante un 
Product Backlog
 dinámico.
Se utilizaron Historias de Usuario bajo el formato BDD (
Behavior-Driven Development
), las cuales fueron priorizadas y refinadas continuamente. La herramienta centralizada de gestión fue el entorno ágil de GitHub (GitHub Projects), lo que permitió la inspección y adaptación constante del equipo ante cualquier cambio.

a. Proceso de Elicitación de Requisitos y Contextualización
Antes de definir las funcionalidades del sistema, es crítico contextualizar la realidad operativa que origina este proyecto. Las ferreterías manejan un inventario masivo estructurado bajo terminología estrictamente técnica. Sin embargo, el cliente común carece de esta base de conocimientos, solicitando los repuestos mediante un lenguaje informal o descriptivo (ej. "la piecita de plástico del tubo"). Esta brecha comunicacional genera fricción, pérdida de tiempo en mostrador y ventas fallidas.
En consecuencia, el proceso de elicitación no se abordó desde un enfoque predictivo tradicional, sino mediante un enfoque ágil. Se aplicaron técnicas de Análisis del Problema de Negocio y definición de Escenarios de Uso para identificar las necesidades centrales del cliente final. A partir de estos hallazgos empíricos, se construyó un 
Product Backlog
 enfocado estratégicamente en la integración de Inteligencia Artificial como un "puente traductor" entre la intención coloquial del usuario y el catálogo técnico del negocio.
b. Requerimientos Funcionales y No Funcionales
Requerimientos Funcionales (RF):
RF01:
 El sistema debe permitir el ingreso de texto en lenguaje coloquial o descripciones imprecisas a través de una barra de búsqueda.

RF04:
 El sistema debe manejar casos vacíos (productos no encontrados) alertando al usuario y mostrando sugerencias útiles sin arrojar errores de servidor.

RNF01 (Interfaz):

 El flujo cognitivo debe ser orquestado mediante n8n. El despliegue debe seguir un esquema distribuido (

 El sistema debe minimizar la latencia de respuesta y el consumo de

RNF05 (Gestión de Configuración):
 El proyecto debe gestionarse a través del control de versiones en GitHub, de forma estructurada y con un README metodológicamente documentado.

Pruebas SQA y Solución al Problema N+1
Durante las pruebas de calidad (SQA), el sistema experimentó un error de concurrencia extrema (Problema N+1). La propuesta inicial pretendía inyectar consejos dinámicos generados por la IA en cada tarjeta de producto. Al renderizar un catálogo de 30 productos, se disparaban 30 peticiones simultáneas, lo que agotaba drásticamente el límite de cuota (
Rate Limit
) de la API y lanzaba un bloqueo por facturación (
payment_required
), causando el colapso de la plataforma.
Para garantizar la disponibilidad, se rediseñó el flujo integrando un Mecanismo de 
Fallback
 (Diccionario Estático Local) en el 
Frontend
. La inferencia de la IA fue restringida exclusiva y estrictamente a la evaluación de la búsqueda principal del usuario. Esta decisión técnica anuló la latencia de la interfaz y estabilizó la aplicación.
Consumo y Optimización de Tokens de IA
La telemetría del consumo del modelo LLM se monitoriza extrayendo estrictamente los metadatos de respuesta de la API, auditando el volumen de 
prompt tokens
 (entrada) y 
completion tokens
 (salida). Como estrategia fundamental de optimización y viabilidad económica, la sinergia entre un 
System Prompt
 diseñado con máxima concisión y la implementación de una Caché en Memoria en el servidor permite que el índice de consumo de tokens para búsquedas recurrentes se reduzca a cero (0). Una vez que una intención ambigua es traducida exitosamente por primera vez, las iteraciones futuras se resuelven localmente en la RAM, garantizando un sistema escalable y financieramente sostenible

h. Arquitectura General de la Aplicación (Sistema Distribuido)
El esquema arquitectónico del Buscador Inteligente se erige sobre un modelo Cliente/Servidor distribuido puro de tres capas (3-Tier Architecture). Para asegurar un entorno de desarrollo estandarizado y modular, se empleó IA en la orquestación inicial del repositorio (scaffolding), cimentando el sistema bajo los preceptos de la Arquitectura Limpia para asegurar una segregación total de responsabilidades:
Capa de Presentación (Frontend):
 Desplegada en la infraestructura Serverless de Vercel y construida en Next.js. Es la encargada de gestionar el estado asíncrono del lado del cliente (
use client
) y la reactividad visual de la interfaz.
Capa de Lógica / Software Intermedio (Backend):
 Alojada de manera independiente en la plataforma Render (Node.js/Express), actúa como el middleware depurador. En esta capa se implementó una estrategia de Caché en Memoria (In-Memory Cache) que actúa como un interceptor. Al recibir una búsqueda idéntica a una previa, el sistema omite el flujo hacia la IA y la BD, despachando los resultados directamente desde la memoria RAM y logrando una latencia casi nula.
Capa de Orquestación e IA:
 El flujo de automatización (n8n) fue autoalojado de forma privada en una Máquina Virtual (VM) Linux en Microsoft Azure, garantizando un entorno aislado y el control absoluto sobre el tráfico de procesamiento de lenguaje natural hacia la API de Google Gemini
i. Arquitectura de la Base de Datos
La estructuración de la información es una etapa fundamental para el desarrollo de soluciones de software robustas y de alta integridad. Para cubrir las exigencias técnicas del buscador, se implementó una base de datos relacional utilizando el motor PostgreSQL, gestionada a través de la plataforma Supabase.
El diseño arquitectónico del repositorio de datos se fundamenta en los siguientes pilares:
Esquema de Datos:
 Se consolidó mediante la especificación rigurosa de las entidades principales (tales como productos, categorías y sustitutos), definiendo sus atributos clave (SKU, denominación técnica, costos) y sus relaciones lógicas.
Indexación y Búsqueda Avanzada (Full-Text Search):
 Para superar las limitaciones de las búsquedas literales básicas (operadores 
LIKE
 / 
ILIKE
), se integró el motor nativo de 
Full-Text Search
 de PostgreSQL. La aplicación de la función 
to_tsquery
, acompañada de un ajuste semántico en el uso de comodines (
wildcards
), permite al sistema tolerar variaciones léxicas, plurales y desinencias gramaticales. Esto garantiza un índice de acierto sumamente alto y mitiga los falsos negativos.
Integridad y Persistencia:
 Se asegura la estabilidad y coherencia en la gestión del inventario, lo que garantiza que la visualización de alternativas y repuestos en tiempo real ofrezca una total fiabilidad operativa.
Manejo de Errores y Casos Vacíos: 
 La resiliencia operativa y la estabilidad gráfica del sistema se garantizaron mediante un control estricto de excepciones lógicas. En escenarios donde la intención de búsqueda es traducida correctamente pero no existe disponibilidad física en el inventario, se configuró el webhook de n8n y el controlador del backend en Node.js para interceptar de forma segura las respuestas de "0 filas" (
zero rows
) provenientes de PostgreSQL. En lugar de desencadenar una excepción no controlada en el servidor o un error HTTP 500 (Internal Server Error), el ecosistema empaqueta un arreglo vacío (
[]
) y lo despacha con un código de éxito HTTP 200 OK. Esta técnica de desarrollo defensivo otorga al frontend la capacidad asíncrona de renderizar un estado vacío (
Empty State
) amigable, guiando al usuario con sugerencias de búsqueda sin comprometer la ejecución de la aplicación.
j. Arquitectura de Automatizaciones (Flujos)
Con el propósito de consolidar la integración del motor de Inteligencia Artificial sin comprometer el rendimiento ni generar acoplamiento en el 
backend
 central de Node.js, se concibió una arquitectura de automatización reactiva fundamentada en eventos, orquestada mediante la herramienta n8n.
Este ecosistema opera bajo un esquema de flujo de trabajo (
workflow
) secuencial, integrado por los siguientes nodos de procesamiento técnico:
Nodo de Entrada (Webhook):
 Encargado de interceptar como disparador las solicitudes provenientes del servidor, capturando eficazmente las descripciones en lenguaje coloquial proporcionadas por el usuario.
Nodo de Procesamiento LLM:
 Establece el vínculo mediante API con el motor de IA, suministrando el 
System Prompt
 necesario para transformar las consultas en un objeto JSON estandarizado bajo terminología técnica.
Nodo de Conexión a Base de Datos:
 Procesa las equivalencias técnicas obtenidas para ejecutar, de forma automatizada, las sentencias SQL hacia PostgreSQL, verificando la disponibilidad en el inventario real.
Nodo de Salida y Manejo de Errores:
 Centraliza y empaqueta la información resultante (SKU, recursos visuales y alternativas sustitutas), canalizándola hacia la capa de presentación. A nivel de estabilidad, implementa una política de manejo seguro para casos vacíos (
zero rows
): si un producto no existe en el inventario, el nodo captura la excepción nativa para evitar caídas del servidor (errores HTTP 500) y retorna un arreglo vacío controlado, lo que permite al 
Frontend
 renderizar un mensaje amigable al cliente
Trabajo Futuro (Fase 2 y Roadmap de Negocio)
 El sistema actual valida con éxito la viabilidad de la tecnología. Para la siguiente iteración, se contempla la siguiente hoja de ruta:
Migración Vectorial:
 Integración de la extensión 
pgvector
 en la base de datos para habilitar búsquedas por absoluta similitud semántica mediante la indexación de 
embeddings
 (vectores matemáticos).
Venta Cruzada por Proyecto:
 Lógica algorítmica de negocio que identificará el "proyecto" del usuario. (Ej. Si el sistema deduce que la intención requiere "pintura", el motor sugerirá autónomamente "lijas", "brochas" y "tirro").
Valor Educativo:
 Generación dinámica de "Mini-tutoriales de Uso Seguro" asociados al repuesto buscado, agregando valor didáctico a la experiencia del comprador común.
